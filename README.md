# Тестовый стенд: Валидация X-Forwarded-For в цепочке Nginx

> Проект реализует безопасную передачу заголовка `X-Forwarded-For` через цепочку из трех обратных прокси-серверов Nginx с гарантированной защитой от подмены (спуфинга) IP-адреса клиентом.

## Архитектура стенда

Стенд развертывается в изолированной Docker-сети `proxy_net` (`172.20.0.0/16`) и состоит из 4 сервисов:

| Сервис | IP-адрес | Порт на хосте | Роль |
| :--- | :--- | :--- | :--- |
| **Nginx 1** | `172.20.0.11` | `8001` | Входная точка (Edge) или промежуточный узел |
| **Nginx 2** | `172.20.0.12` | `8002` | Промежуточный узел или входная точка |
| **Nginx 3** | `172.20.0.13` | `8003` | Последний прокси перед приложением или входная точка |
| **App** | `172.20.0.100` | `-` | Python HTTP-сервер, возвращающий полученные заголовки в JSON |
| **Docker Gateway** | *Назначается Docker* | `-` | Шлюз хост-машины (считается внешним недоверенным клиентом) |

### Сценарии маршрутизации
Запрос от пользователя может прийти на любой из портов Nginx и пройти по любому допустимому маршруту:
1. `Client → Nginx 3 → App` (прямой запрос к последнему узлу)
2. `Client → Nginx 2 → Nginx 3 → App` (через два прокси)
3. `Client → Nginx 1 → Nginx 2 → Nginx 3 → App` (полная цепочка)

## Протокол тестирования (curl)

Ниже приведен протокол ручной проверки выполнения всех требований с помощью утилиты `curl`.

> **Важно:** Первый IP в цепочке (`<IP_ХОСТА>`) зависит от сетевого окружения вашей хост-машины (обычно это IP шлюза Docker-сети, например, `172.20.0.1` или `172.17.0.1`). Валидация фокусируется на корректном добавлении IP прокси-серверов в конец цепочки.

### Требование 1: Получение полной цепочки IP
Приложение должно получить IP-адрес пользователя и всех Nginx, через которые прошел запрос.

```bash
# 1. Запрос через полную цепочку (порт 8001)
curl -s http://localhost:8001 | jq '.x_forwarded_for'
# Ожидаемый результат: "<IP_ХОСТА>, 172.20.0.11, 172.20.0.12, 172.20.0.13"

# 2. Запрос через два прокси (порт 8002)
curl -s http://localhost:8002 | jq '.x_forwarded_for'
# Ожидаемый результат: "<IP_ХОСТА>, 172.20.0.12, 172.20.0.13"

# 3. Прямой запрос к последнему прокси (порт 8003)
curl -s http://localhost:8003 | jq '.x_forwarded_for'
# Ожидаемый результат: "<IP_ХОСТА>, 172.20.0.13"
```

### Требование 2: Защита от спуфинга (подмены) заголовка
Приложение не должно получить заголовок `X-Forwarded-For`, который недобросовестный пользователь может добавить в свой запрос.

```bash
# 1. Прямой запрос к Nginx 1 с подменой заголовка
curl -s -H "X-Forwarded-For: 10.99.99.99" http://localhost:8001 | jq '.x_forwarded_for'
# Ожидаемый результат: "<IP_ХОСТА>, 172.20.0.11, 172.20.0.12, 172.20.0.13"
# Вывод: Фейковый IP отброшен, полная цепочка прокси построена корректно.

# 2. Прямой запрос к Nginx 2 с подменой заголовка
curl -s -H "X-Forwarded-For: 10.99.99.99" http://localhost:8002 | jq '.x_forwarded_for'
# Ожидаемый результат: "<IP_ХОСТА>, 172.20.0.12, 172.20.0.13"
# Вывод: Фейковый IP отброшен, цепочка прокси построена корректно.

# 3. Попытка подделать IP при прямом запросе к Nginx 3
curl -s -H "X-Forwarded-For: 10.99.99.99" http://localhost:8003 | jq '.x_forwarded_for'
# Ожидаемый результат: "<IP_ХОСТА>, 172.20.0.13"
# Вывод: Фейковый IP 10.99.99.99 полностью отброшен, подставлен реальный IP отправителя.
```

## Архитектурные решения

### 1. Разграничение доверия (`geo` + `map`)
Главная проблема при тестировании с локальной машины: запросы приходят с IP шлюза Docker. Если доверять всей подсети `/16` без исключений, Nginx посчитает запросы с хоста "доверенными" и пропустит фейковый заголовок.

**Решение:** Явное исключение шлюза из списка доверенных узлов в `nginx/common.conf`:
```nginx
geo $is_trusted_proxy {
    172.20.0.0/16   1;  # Доверяем внутренним контейнерам
    172.20.0.1      0;  # Шлюз хоста считаем внешним (недоверенным) клиентом
    default         0;
}
map $is_trusted_proxy $trusted_xff {
    1   $http_x_forwarded_for;  # Запрос от прокси: сохраняем переданную цепочку
    0   $remote_addr;           # Запрос с хоста: игнорируем заголовок клиента, начинаем цепочку с реального IP
}

В конфигурации geo шлюз 172.20.0.1 явно указан как недоверенный (0). Если Docker на вашей системе назначит шлюзу другой IP-адрес, его необходимо добавить в этот список со значением 0, чтобы логика защиты от спуфинга работала корректно.

### 2. Почему не использован модуль `real_ip`?
Использование стандартного модуля `real_ip` создает технический парадокс в данной топологии:
- **Либо уязвимость:** При доверии ко всей подсети `/16` модуль пропускает поддельные заголовки с хост-машины.
- **Либо хардкод:** При доверии только к IP прокси (`.11`, `.12`, `.13`) теряется динамичность конфигурации.
- **Дублирование:** Раннее переопределение переменной `$remote_addr` этим модулем приводит к каскадному дублированию IP-адресов в заголовке.

Связка `geo` + `map` элегантно решает эту задачу: она проверяет *исходный* IP соединения до любых его изменений, обеспечивая строгую безопасность без привязки к жестким адресам.

## Управление и отладка

Все основные операции вынесены в `Makefile`. Для глубокой диагностики используются кроссплатформенные команды Docker.

| Команда | Описание |
| :--- | :--- |
| `make build` | Сборка образов (включая Python-приложение) |
| `make up` | Запуск стенда в фоновом режиме |
| `make test` | Запуск автоматической bash-валидации |
| `make down` | Остановка и удаление контейнеров, сетей и volumes |
| `make logs` | Просмотр логов всех сервисов (последние 50 строк) |
| `docker compose ps` | Проверка статуса и состояния здоровья (health) контейнеров |
